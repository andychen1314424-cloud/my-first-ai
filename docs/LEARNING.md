# 四次小练习，学会这套工具

先运行 README 的启动步骤。每次只完成一个练习，记录「我改了什么 → 怎么验证 → 遇到什么问题」。下面的时长只是练习预算，不是完成保证。

## 练习 1：看懂产品输入（约 20–30 分钟）

打开 `src/NewProject.tsx`，找出 `brief` 的五个字段。分别填写一个过大的想法和一个很小的想法，对比模型计划是否更容易完成。

动手：把一个示例按钮改成你经常遇到的小需求；不要在提交到公共仓库的示例中放客户资料或个人记录。

验收：点击新按钮能正确填入想法和学习重点；空输入仍不能生成。写一句话解释：这个产品的输入、处理、输出分别是什么。

## 练习 2：修改提示词，验证输出（约 30–60 分钟）

打开 `shared/domain.ts` 的 `buildMessages`。页面上的「看看这个功能背后的提示词」显示同一份内容。修改任务要求，例如更强调“先写一个输入输出样例”，并更新 `PROMPT_VERSION`。

保留相同的想法、模型和限制，比较修改前后的结果，记录任务是否具体、验收是否可操作。一次改一个要求。

验收：输出仍符合 `PLAN_SCHEMA`，`npm run check` 通过；旧项目仍能看到旧提示词快照。不要只因一条结果更顺眼，就声称质量全面提升。

## 练习 3：追踪一次接口与失败（约 30–45 分钟）

在浏览器开发者工具的 Network 中找到 `POST /api/projects`。对照 `src/api.ts`、`server/app.ts` 和 `server/ollama.ts`，找出输入验证、模型请求、结果验证和保存发生在哪里。

动手：生成前退出 Ollama，观察错误提示；重新启动后重试。

验收：失败时没有新项目出现，原始表单内容仍在；恢复服务后能继续生成。解释为什么只在前端验证输入还不够。

## 练习 4：完成一个自己的自动化迭代（约 60 分钟起）

选一个小改动，例如给项目增加“我遇到的阻碍”字段，或增加只看未完成任务的筛选。先写一个具体触发条件和完成标准，再修改界面或数据类型。

如果改了持久化结构，先设计旧数据如何读取；不要直接清空真实数据库。可以在临时目录启动一份实验数据：

```bash
# macOS / Linux 示例；Windows 用 PowerShell 的 $env:ZX_DATA_DIR
ZX_DATA_DIR=./.data/practice npm start
```

验收：重启后该保存的信息仍在；现有功能通过检查。最后在这个工具里写下复盘，再把修改提交到新分支。

## 自查问题

- 为什么“返回 JSON”与“返回符合要求的项目”是两件事？
- 点击勾选与输入复盘，分别什么时候会保存？
- 为什么两个窗口编辑同一项目时需要 `revision`？
- 模拟接口测试能证明什么，哪些必须用真实模型测试？
- 这个版本自动完成了哪段流程，哪些工作仍然是你自己做？
